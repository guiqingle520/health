# 开发设计与迭代计划

## 1. 开发原则

- 先稳定 Current 主路径，再扩展 Next 功能。
- 所有用户健康数据读写最终都应绑定当前登录用户。
- 文档中的 Future 仅作为模块方向，不一次性实现。
- 前后端字段命名保持 API camelCase、数据库 snake_case。
- companion context 始终是用户健康解释层。

## 2. 当前代码基线

### 后端

- NestJS `AuthModule`：登录、当前用户、token 刷新。
- NestJS `HealthModule`：档案、饮食、运动、历史、日汇总、仪表盘。
- PostgreSQL Repository：已对接 `m1_m2_schema.sql` 中的核心表。
- e2e：覆盖登录、建档、饮食/运动写入、历史查询、日汇总、仪表盘。

### 移动端

- Flutter 单文件主流程。
- `AppStage`：login、onboarding、dashboard。
- `ApiClient`：对接登录、档案、仪表盘、历史记录等接口。

## 3. 开发周期总览

默认按 2 周一个 Sprint 规划，主版本周期为 14 周，扩展生态预留 4 周。若团队规模为 1 名前端、1 名后端、1 名测试兼职，建议按下表执行；如团队更小，应优先保证 Sprint 1-4。

| Sprint | 周期 | 目标 | 主要交付物 | 依赖 |
|---|---|---|---|---|
| Sprint 0 | 第 1 周 | 项目准备与基线稳定 | 环境、数据库、CI 命令、文档冻结、任务拆分 | 无 |
| Sprint 1 | 第 2-3 周 | 当前主路径强化 | 登录/建档/首页重构、鉴权写入接口、错误态 | Sprint 0 |
| Sprint 2 | 第 4-5 周 | 底部导航与基础功能页 | 首页、数据、AI 建议、我的页 UI 骨架 | Sprint 1 |
| Sprint 3 | 第 6-7 周 | 记录增强与趋势基础 | 饮水/睡眠/指标事件、趋势接口、数据页联调 | Sprint 2 |
| Sprint 4 | 第 8-9 周 | AI 建议与报告 MVP | 规则型建议、建议状态、报告 JSON 摘要 | Sprint 3 |
| Sprint 5 | 第 10-11 周 | Garmin 接入一期 | OAuth 授权、连接状态、backfill、同步日志 | Garmin 开发者权限 |
| Sprint 6 | 第 12-13 周 | Garmin 数据入业务 | 指标标准化、趋势/首页/AI 使用 Garmin 数据 | Sprint 5 |
| Release | 第 14 周 | 联调、验收、灰度准备 | 回归测试、验收清单、发布说明 | Sprint 1-6 |
| Sprint 7 | 第 15-16 周 | 家庭共享一期 | 家庭成员、授权范围、共享入口 | Release |
| Sprint 8 | 第 17-18 周 | Pro 与生态预研 | Pro 权益、深度报告方向、设备多厂商预留 | Release |

### 里程碑

- M1：第 3 周末，登录、建档、首页主路径可稳定演示。
- M2：第 5 周末，底部导航四个主页面可演示。
- M3：第 9 周末，数据趋势、AI 建议、报告 MVP 可联调。
- M4：第 13 周末，Garmin 授权与指标入库闭环完成。
- M5：第 14 周末，完成主版本验收。

### 优先级

- P0：登录、建档、鉴权、首页、饮食/运动记录、日汇总、基础测试。
- P1：底部导航、数据趋势、AI 建议、我的页、报告摘要。
- P2：Garmin Health API 接入、设备指标标准化。
- P3：家庭共享、Pro 会员、多厂商设备、医生/顾问视图。

## 5. 迭代执行计划

### Iteration 1 - 当前主路径强化

- 周期：Sprint 1，第 2-3 周。
- 移动端重构为页面和组件拆分。
- 登录页增加协议、验证码状态、错误提示。
- 建档页增加表单校验。
- 仪表盘增加空态、错误态、刷新态。
- 后端将饮食/运动写入迁移到鉴权当前用户接口。
- 验收：登录 -> 建档 -> 首页 -> 记录 -> 仪表盘刷新闭环可用。

### Iteration 2 - 底部导航与功能页

- 周期：Sprint 2，第 4-5 周。
- 新增底部导航：首页、数据、AI 建议、我的。
- 数据页先接入模拟或后端趋势接口。
- 我的页先接入档案、目标、记录历史和设置入口。
- UI 样式以 `UI/` 原型为准。
- 验收：四个 Tab 可切换，页面空态和错误态完整。

### Iteration 3 - 数据趋势与报告

- 周期：Sprint 3-4，第 6-9 周。
- 后端新增趋势聚合接口。
- 新增 `health_metric_events` 或按现有记录聚合的过渡实现。
- 报告生成先返回 JSON 摘要，再扩展 PDF 导出。
- 验收：周/月/年趋势可切换，报告摘要能展示核心指标和建议。

### Iteration 4 - AI 建议

- 周期：Sprint 4，第 8-9 周。
- 先实现规则型建议：饮水、睡眠、运动、饮食。
- 记录建议状态：pending、accepted、dismissed、snoozed。
- 后续再接入 AI 服务和拍照识别。
- 验收：建议列表可展示，采纳/稍后/忽略状态可追踪。

### Iteration 5 - Garmin 设备接入

- 周期：Sprint 5-6，第 10-13 周。
- 申请并配置 Garmin Health API 开发者权限、OAuth redirect URI、webhook endpoint。
- 实现 `connected_devices`、`device_sync_logs`、`health_metric_events`。
- 实现 Garmin OAuth 授权、callback、断开连接。
- 实现 backfill 与 webhook 数据标准化。
- 将步数、心率、睡眠、压力、血氧、Body Battery 等指标接入趋势、首页和 AI 建议。
- 验收：授权、同步、断开、重复 webhook、token 失效等场景通过。

### Iteration 6 - 家庭、Pro 与生态扩展

- 周期：Sprint 7-8，第 15-18 周。
- 家庭共享先做邀请和授权范围。
- Pro 会员只控制权益，不耦合业务实现。
- 多厂商设备只做接口和数据模型预留。

## 6. 前端设计要求

- 采用底部导航后，登录/建档不显示底部导航，业务页显示底部导航。
- 首页保留健康分和今日核心指标，不堆叠太多入口。
- 数据页图表需要有空态和异常提示。
- AI 建议页每条建议需要解释原因和可执行动作。
- 我的页可以是长滚动页，按健康档案、报告、家庭、设置、帮助分组。

## 7. 后端设计要求

- 新接口默认使用 `JwtAuthGuard`。
- 当前用户资源使用 token 中的 `sub`，不要信任客户端传入 `userId`。
- 列表接口统一支持 `from`、`to`、`limit` 或明确分页参数。
- 趋势接口需要允许无数据返回空 points。
- AI 建议接口需要记录用户动作，避免重复推荐同一条建议。
- Garmin 接入必须使用官方 Health API 或 Health SDK；不使用非官方抓取。
- Garmin token 加密存储，不写入日志，不返回客户端。
