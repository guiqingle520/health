# 开发设计与迭代计划

## 1. 开发原则

- 先稳定 Current 主路径，再扩展 Next 功能。
- 所有用户健康数据读写最终都应绑定当前登录用户。
- 文档中的 Future 仅作为模块方向，不一次性实现。
- 前后端字段命名保持 API camelCase、数据库 snake_case。
- companion context 始终是用户健康解释层。
- Redis 作为 Next 阶段缓存中间件引入，只做热点读缓存、短期状态、限流和同步锁，不作为健康数据权威存储。
- 后续所有开发默认必须支持多语言，用户可见文案不得新增单语言硬编码。
- 如遇临时占位或不可翻译内容，必须在实现前补齐翻译资源或明确标注并确认。

## 2. 当前代码基线

### 后端

- NestJS `AuthModule`：登录、当前用户、token 刷新。
- NestJS `HealthModule`：档案、饮食、运动、历史、日汇总、仪表盘。
- PostgreSQL Repository：已对接 `m1_m2_schema.sql` 中的核心表。
- e2e：覆盖登录、建档、饮食/运动写入、历史查询、日汇总、仪表盘。

### 移动端

- Flutter 单文件主流程。
- `AppStage`：login、onboarding、dashboard。
- `ApiClient`：对接登录、档案、仪表盘、历史记录等接口。

## 3. 开发周期总览

默认按 2 周一个 Sprint 规划，主版本周期为 14 周，扩展生态预留 4 周。若团队规模为 1 名前端、1 名后端、1 名测试兼职，建议按下表执行；如团队更小，应优先保证 Sprint 1-4。

| Sprint | 周期 | 目标 | 主要交付物 | 依赖 |
|---|---|---|---|---|
| Sprint 0 | 第 1 周 | 项目准备与基线稳定 | 环境、数据库、CI 命令、文档冻结、任务拆分、国际化基础 | 无 |
| Sprint 1 | 第 2-3 周 | 当前主路径强化 | 登录/建档/首页重构、鉴权写入接口、错误态、语言切换框架 | Sprint 0 |
| Sprint 2 | 第 4-5 周 | 底部导航与基础功能页 | 首页、数据、AI 建议、我的页 UI 骨架 | Sprint 1 |
| Sprint 3 | 第 6-7 周 | 记录增强与趋势基础 | 饮水/睡眠/指标事件、趋势接口、数据页联调 | Sprint 2 |
| Sprint 4 | 第 8-9 周 | AI 建议与报告 MVP | 规则型建议、建议状态、报告 JSON 摘要 | Sprint 3 |
| Sprint 5 | 第 10-11 周 | Garmin 接入一期 | OAuth 授权、连接状态、backfill、同步日志 | Garmin 开发者权限 |
| Sprint 6 | 第 12-13 周 | Garmin 数据入业务 | 指标标准化、趋势/首页/AI 使用 Garmin 数据 | Sprint 5 |
| Release | 第 14 周 | 联调、验收、灰度准备 | 回归测试、验收清单、发布说明 | Sprint 1-6 |
| Sprint 7 | 第 15-16 周 | 家庭共享一期 | 家庭成员、授权范围、共享入口 | Release |
| Sprint 8 | 第 17-18 周 | Pro 与生态预研 | Pro 权益、深度报告方向、设备多厂商预留 | Release |

### 里程碑

- M1：第 3 周末，登录、建档、首页主路径可稳定演示。
- M2：第 5 周末，底部导航四个主页面可演示。
- M3：第 9 周末，数据趋势、AI 建议、报告 MVP 可联调。
- M4：第 13 周末，Garmin 授权与指标入库闭环完成。
- M5：第 14 周末，完成主版本验收。

### 优先级

- P0：登录、建档、鉴权、首页、饮食/运动记录、日汇总、基础测试。
- P1：底部导航、记录中心、数据趋势、AI 建议、报告与分享、通知提醒和目标设定、我的页、报告摘要。
- P2：Garmin Health API 接入、设备指标标准化。
- P3：家庭共享、Pro 会员、多厂商设备、医生/顾问视图、隐私数据权利、运营后台。

## 4. 每周开发计划

### 第 1 周 - 项目准备与基线稳定

| 维度 | 计划 |
|---|---|
| 目标 | 确认当前代码、环境、数据库、文档和任务拆分可支撑后续开发。 |
| 前端 | 梳理 `apps/mobile/lib/main.dart`，拆分页面、组件、API client 的目标目录结构；确认 UI 原型对应页面清单。 |
| 后端 | 确认 PostgreSQL 连接、`m1_m2_schema.sql`、HealthRepository、e2e 基线；整理当前接口 Current 清单。 |
| 缓存 | 确认 Redis 部署方式、`REDIS_URL`、`CACHE_ENABLED`、本地开发降级策略；不在第 1 周强行改业务逻辑。 |
| 国际化 | 确认 `zh-Hans`、`zh-Hant`、`en`、`ja`、`ko` 的资源目录、locale normalization 和偏好存储方案。 |
| 测试/文档 | 固化验收命令、测试数据、接口样例；建立缺陷和风险清单。 |
| 交付物 | 任务看板、开发分支策略、环境说明、基线测试结果、Redis 环境配置说明、i18n 资源结构。 |
| 验收 | 后端 build/test 能运行；移动端能启动主流程；团队对 Sprint 1 范围无歧义。 |

## 6. 前端设计要求

- 采用底部导航后，登录/建档不显示底部导航，业务页显示底部导航。
- 首页保留健康分和今日核心指标，不堆叠太多入口。
- 数据页图表需要有空态和异常提示。
- AI 建议页每条建议需要解释原因和可执行动作。
- 我的页可以是长滚动页，按健康档案、报告、家庭、设置、帮助分组。

## 7. 后端设计要求

- 新接口默认使用 `JwtAuthGuard`。
- 当前用户资源使用 token 中的 `sub`，不要信任客户端传入 `userId`。
- 列表接口统一支持 `from`、`to`、`limit` 或明确分页参数。
- 趋势接口需要允许无数据返回空 points。
- AI 建议接口需要记录用户动作，避免重复推荐同一条建议。
- Garmin 接入必须使用官方 Health API 或 Health SDK；不使用非官方抓取。
- Garmin token 加密存储，不写入日志，不返回客户端。
- Redis 缓存必须采用 cache-aside，所有缓存 key 包含用户作用域或明确的系统作用域。
- Redis 故障不得导致核心读写接口失败；缓存 get/set/delete 失败只记录日志。
- 写接口在数据库提交成功后再失效缓存；缓存失效失败不回滚业务事务。
- 不缓存 Garmin token、refresh token 明文、验证码明文、报告文件本体等敏感数据。

## 8. 错误处理

### Next 建议错误码

- `AUTH_REQUIRED`
- `PROFILE_NOT_FOUND`
- `VALIDATION_FAILED`
- `RESOURCE_FORBIDDEN`
- `RESOURCE_NOT_FOUND`
- `AI_SERVICE_UNAVAILABLE`

移动端需要将错误展示为页面内提示，不使用阻塞式弹窗作为主反馈。

- 后端：`npm run backend:test`、`npm run backend:build`。
- 移动端：Flutter 手动主流程验证；后续补 widget test。

## 10. 风险与缓冲

- Garmin Health API 审批可能影响 Sprint 5 开始时间；若审批延迟，先实现设备连接表、模拟 provider、趋势消费链路。
- AI 服务未接入前，先使用规则型建议保证业务闭环。
- PDF 报告复杂度可控，首期先返回 JSON 报告摘要。
- 家庭共享涉及隐私授权，必须等权限模型稳定后再进入实现。
- Redis 引入后需要关注缓存一致性和故障降级；首期通过短 TTL、主动删除和降级到数据库路径降低风险。
